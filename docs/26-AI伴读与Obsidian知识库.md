# AI 伴读 + Obsidian 知识库（0.13.0 设计）

> 起因：抖音「清华姜学长」那条 video（419 秒，字幕已整理在 `docs/调研-姜学长AI伴读助手视频字幕.md`）。
> 他演示的玩法是 **Obsidian 存笔记 + WorkBuddy 读原书**，只需要「一本电子书 + 一段提示词」。
> 本文把这个玩法落到 dsh-reading 现有的代码上，并补上他没解决的一半：**读者的「问 AI」记录本身就是素材**。
> 状态：**只做设计，不写码**。

## 〇、先说结论

dsh-reading 已经有的东西，正好是那条视频缺的最难的一半：

| 那条视频 | dsh-reading 现状 |
|---|---|
| 读原书 | 书架 10 本、EPUB 内存解析、目录、全文搜索、CFI 锚点 —— **已有** |
| 答问 | 问 AI 五模式（`lib/askpresets.js`），走宿主子代理 —— **已有** |
| 整理文件 | 按章蒸馏 + 全书骨架（`lib/distill.js`）+ 导出 Markdown —— **已有** |
| 存笔记 | 只能「下载 .md」到浏览器下载目录 —— **缺自动落盘** |
| 四类笔记 | 只有「蒸馏稿」一类 —— **缺全书地图 / 人物关系 / 思想脉络** |
| 问完自动写回 | 没有 —— **缺，这是灵魂** |

所以这一版不是从零做大功能，而是**把已有的三样东西接上一个出口**：写进用户的 Obsidian 库。
外加一件他视频里没做、但我们数据条件更好的事：**拿「问过什么」去个性化笔记**（见 §6）。

三句话概括：

1. **写出去**：蒸馏稿 + 标注 + 问答，自动落成 Obsidian 里的四类 Markdown。
2. **写回去**：每问一个问题，结论自动归位到对应笔记，用户不用点保存。
3. **按人写**：同一个读者在这本书里的提问分布，决定笔记写给谁看。

## 一、不做什么（先划边界）

这几条是硬边界，写进 `docs/23` 已有的桥接规范，不新开一套：

- **只往 `<vault>/dsh-reading/` 里写**，vault 根目录跟别人的笔记一个字都不碰。
- **不做双向同步**。用户在 Obsidian 里改了笔记，下次同步不覆盖他改的那一段（§4 的锚块协议），但也不会反向改书库。
- **不装 Obsidian 插件、不开 Local REST API、不模拟点击 Obsidian**。vault 就是个文件夹，写文件够了（这条 `docs/23` 已经论证过）。
- **不把 vault 里已有的读书笔记当书的原文**喂给 AI。别人的观点混进「原文」是最难查的一类错。
- **不自动启动别人的软件**，只探测路径是否存在。

## 二、落盘目标：四类产物

按视频里的四类，落成四个文件。名字定死，用户不用想：

```
<vault>/dsh-reading/
├── 《如何阅读一本书》-08773db717b9d75d/
│   ├── 《如何阅读一本书》 00 全书地图.md
│   ├── 《如何阅读一本书》 01 读书笔记.md
│   ├── 《如何阅读一本书》 02 人物关系.md
│   └── 《如何阅读一本书》 03 思想脉络/
│       ├── 检视阅读与分析阅读的分界.md
│       └── 主动阅读到底主动在哪.md
└── _索引/
    ├── 我的阅读.md
    └── 主题总览.md
```

**为什么文件夹按书分、文件名还带书名前缀**：Obsidian 的 `[[链接]]` 默认按文件名全库解析，十本书就有十个 `00 全书地图`，
裸链会连错。带上书名之后 `[[《如何阅读一本书》 00 全书地图]]` 在任何地方都唯一，用户手打也认得出来。
文件夹负责「书多了不挤在根目录」，文件名负责「链接不歧义」，两件事分开做。

**文件夹名带 hash 前 16 位**：同名书不冲突（《活着》两个版本很常见）；用户改文件夹名也不影响——台账里存的是 hash，
下次同步按 hash 重新定位，找不到就在新位置重建（并提示一句）。

### 四个文件各写什么

| 文件 | 内容 | 数据来源 | 频率 |
|---|---|---|---|
| **00 全书地图** | 一句话这本书在讲什么 / 分几个阶段 / 阶段之间怎么衔接 / 读它需要什么前置 | `skeleton`（已有）+ 目录 | 一次性，可重做 |
| **01 读书笔记** | 按章分小节：要点、可回源的原句、我的批注、**讨论记录**（问 AI 的结论） | `distill.chapters` + `annotations.jsonl` + `qa.jsonl` | 增量，问一次长一点 |
| **02 人物关系** | Mermaid `graph LR`，节点是人，边是关系（带原文依据） | AI 抽 + 原文核对 | 一次性，可重做 |
| **03 思想脉络/** | 每篇一个主题：这个说法从哪来、书里怎么用、别处怎么用、我现在的判断 | 讨论记录聚出来的主题 | 主题够 3 条讨论就成篇 |

「02 人物关系」对非小说没有意义（《如何阅读一本书》里没有人物）。所以这一份是**按书是否小说决定要不要生成**，
判据用现成的 `meta.category` / `meta.tags`，判不出来就不生成，不硬凑。

## 三、写文件的四条铁规矩

Obsidian 库是用户的地盘，写坏了比不写更糟。四条：

1. **原子写**。先写 `xxx.md.tmp` 再 `rename`，中途断电不会留半个文件。
2. **覆盖前备份**。旧文件落到 `<vault>/dsh-reading/.history/<相对路径>/<时间戳>.md`，保留 20 份（沿用 `lib/store.js:86` 的 `HISTORY_KEEP`）。
3. **路径必须在 vault 内**。用现成的 `LibraryPaths.assertInside()`（`lib/paths.js:115`）同款判断：`base + sep` 前缀比对，不用裸 `startsWith`。
4. **编码固定**：UTF-8 无 BOM、`\n` 换行、结尾一个换行。Windows 上编辑过的文件 CRLF 会让 diff 花掉。

## 四、锚块协议（这一节是整份设计的核心）

问题很具体：**同步一次要覆盖整个文件，但用户在 Obsidian 里手写过东西**。

解法不是「合并 Markdown」（那是地狱），而是**只写自己那一块**：

```markdown
<!-- dsh-reading:block id=a3f2 kind=discuss chapter=ch003 -->
### 2026-11-17 22:10 · 阅读的四个层次是并列的吗

> **问**：检视阅读和分析阅读是并列关系吗？
>
> **答**：不是并列，是包含与被包含……（摘自第四章）

- 关联原句：「检视阅读是系统化略读的一门艺术。」（第四章）
<!-- dsh-reading:end id=a3f2 -->
```

规则五条：

1. **块外的一切归用户**。重写时只替换 `start` 与 `end` 之间的字节，块外的段落、标题、图片、附件一律不碰。
2. **幂等**。同一个 `id` 重写多少次，文件字节都一样（时间戳也来自记录本身，不用 `Date.now()`）。
3. **用户改过块里的字 → 不覆盖**。台账里存块内容的 `sha256`，同步前重算，不一致就把这条标成 `user-edited`，
   整块跳过并在界面上说一句「有 3 段你改过，我没有覆盖」。
4. **用户删了整块 → 不复活**。台账记 `deletedByUser`，以后再也不往那个位置加（否则用户每删一次都要再删一次）。
5. **块 id 稳定**。来自来源记录的 id（标注 id / qa 的 ULID），不是序号——序号一插入就全错位。

为什么用 HTML 注释而不是 YAML 或自定义标记：Obsidian 阅读视图里 HTML 注释不显示，源码模式看得见，也不会被 Markdown 解析器吃掉。

## 五、自动写回：问完就有痕迹

视频里那句「用户没点保存，回到 Obsidian 就看见已在里面了」是整个玩法的灵魂。这里分两级实现，**默认走零 AI 的 L0**。

### L0 机械归位（默认，零 AI 开销）

`qa.ask`（`lib/routes.js:956`）成功之后，宿主**不等前端**，直接把这个 qa 记录归位：

```
输入：{ question, answer, mode, chapterHref, chapterLabel, selectedText, id }
输出：{ targetFile, blockId, blockText }
```

判定顺序：

1. 问题里出现的术语命中了 `03 思想脉络/` 已有主题页的标题或别名 → 追加到那一页的「讨论记录」
2. 否则命中已有章节小节（`chapterHref` 相同）→ 追加到 `01 读书笔记` 对应章的讨论区
3. 否则新建该章的小节，再追加
4. 全书地图 / 人物关系不参与 L0

L0 不调 AI，只做字符串匹配和 Markdown 拼接，几十毫秒。**失败不阻断问答**：写盘失败只在界面上留一条「有 2 条讨论没写进 Obsidian」，
问答本身照常返回（用户要的是答案，不是日志）。

### L1 AI 提炼（用户点一下才跑）

「整理成笔记」按钮 → 拿这一章/这本书最近 N 条讨论块 + 章节原文 → 让 AI 收束成 3–5 条判断，写进 `01 读书笔记` 的「要点」锚块，
**原来的讨论块保留不动**（用户可能要看原话）。

为什么不一问完就 L1：一次问答已经 90 秒超时（`ask.js` 的 `ASK_TIMEOUT_MS`），再叠一次调用会让人以为卡死；
而且频繁重写要点区会把用户的阅读节奏打断。

### 开关

`settings.obsidianAutoWrite`（默认 `true`）。关掉之后只剩手动「同步到 Obsidian」。
默认值选 `true` 是因为视频里那个效果靠它；但要给一个明确的关法，不能让用户找不到。

## 六、用「问 AI」的记录个性化笔记

这是用户特别点名要加的一半，也是相对视频的增量。

### 6.1 先分清两种用法，别混

| 用法 | 输入 | 输出 | 风险 |
|---|---|---|---|
| **画像** | `qa.jsonl` 的统计特征 | 一段 100 字左右的「这位读者」 | 低，但可能过度解读 |
| **归档** | 单条 qa 的原文 | §4 的讨论块 | 低，但要脱敏/去重 |

**画像不是把问答原样塞进 prompt**。一本书问过 30 个问题、每条 400 字，塞进去就是 12000 字噪声，
而且模型会去复述这些问题而不是写笔记。画像只进**结论**，不进原文。

### 6.2 画像长什么样

存 `<bookDir>/reader-profile.json`：

```json
{
  "version": 1,
  "bookHash": "08773db...",
  "updatedAt": "2026-11-17T14:22:00.000Z",
  "askedCount": 23,
  "modes": { "concept": 11, "general": 8, "classic": 4 },
  "chapters": [{ "href": "text/ch003.xhtml", "label": "第三章 阅读的第一个层次", "count": 9 }],
  "focus": ["检视阅读", "主题阅读", "主动阅读", "笔记方法"],
  "habits": ["习惯先问定义再问用法", "关心可执行步骤"],
  "note": "这位读者在乎术语的来路与边界，笔记要给出处、少形容。"
}
```

**全部字段都能在零 AI 下算出来**（`modes` / `chapters` / `focus` 用频次 + 停用词），
`habits` 与 `note` 才要 AI，且是**可缺省**的：缺了照样能用。

### 6.3 注进哪些 prompt

三处，都只加一段，不改原有要求：

1. `distill.chapter` —— 决定一章的「要点」写成术语卡还是步骤卡
2. `distill.skeleton` —— 决定全书地图是给「想读懂」的人看还是给「想用」的人看
3. 新建 `03 思想脉络` 页 —— 决定主题页要不要写「我的判断」这一段

写法上是**追加到 requirements 末尾的一条**，不是替换 persona：persona 管「你是谁」，画像管「这次写给谁」。

### 6.4 界面上要看得见

> 这本书你问过 **23** 个问题，**9** 个集中在第三章；
> 多半在问术语（11 次「概念溯源」）。笔记会给出处，少形容。
> [ 重新分析 ] [ 关掉个性化 ]

不解释「什么是画像」，就说「你问过什么、我据此怎么写」。关掉之后所有笔记走通用口径。

### 6.5 一个必须防的坑

画像会**自我强化**：模型按画像写笔记 → 用户读到更对味的笔记 → 继续按同样的方式问 → 画像更极端。
所以：

- `focus` 取「最近 30 条 + 全部」两套，新出现的主题要能顶上来；
- 界面上那句话里的数字必须是真的（从 json 读，不编）；
- 提供「重新分析」，让用户能手动重算一次。

## 七、跨书：思想脉络怎么成篇

视频里最漂亮的一步：**追问可以跨出这本书**（「还有哪些作品做过类似处理、这种写法怎么演变」），收束成一句判断，
升格成一篇独立主题。

### 7.1 主题从哪来

`thread`（主题）的判定用机械聚类，不调 AI：

1. 从所有书的讨论块里抽关键词（用户问题 + 答案里的名词短语，去掉停用词）
2. 同一个关键词在 **≥2 本书**、**≥3 个讨论块**里出现 → 立一个候选主题
3. 用户点「立成主题」才建 `_索引/主题总览.md` 里的一行

为什么不一上来就让 AI 聚类：误报的主题页比没有更烦人，用户会攒一屏「X 与 Y 的关系」什么也没说。
机械筛选保守一点，让用户自己点头。

### 7.2 主题页结构

```markdown
# 检视阅读与分析阅读的分界

> 出现在 3 本书、7 段讨论 · 最后更新 2026-11-17

## 这本书里怎么说
- 《如何阅读一本书》第四章 …（原句）

## 别的书怎么处理
- 《…》第十二章 …（原句）

## 我现在的判断
（空着，等用户自己写 —— 这一格不由 AI 填）

## 讨论记录
<!-- dsh-reading:block ... -->
```

**「我现在的判断」这一格留空**。视频里那一步是「收束成哪一句判断」——那是读者的活。
AI 填了就把读者的位置占了，三个月后他自己也分不清哪句是自己的。

### 8.3 书架卡片

## 九、宿主侧代码怎么组织

沿用现有的「一个文件一件事 + 路由表加行」的写法，不引依赖。

```
lib/
  vault.js        —— vault 探测、路径校验、原子写、备份、锚块读写（唯一碰文件的地方）
  blocks.js       —— 锚块协议：parse / render / diff（纯函数，可单测）
  notesync.js     —— 四类产物的组装：map / note / relations / threads → 调 vault.js 落盘
  profile.js      —— 读者画像：统计 + 缓存 reader-profile.json
  threads.js      —— 跨书主题聚类（纯函数）
  bridges/obsidian.js —— 薄壳：把 vault.js 包成 docs/23 那个适配器形状（id/label/detect/list/fetch/annotations/write）
```

### 新增路由（照旧 `POST /api/dsh-reading/<method>`）

| 方法 | 入参 | 返回 |
|---|---|---|
| `vault.detect` | — | `{ found, vaults:[{path,name}], chosen }` |
| `vault.choose` | `{ path }` | `{ ok, path }`（校验是目录、可写、不是根目录） |
| `notes.status` | `{ bookHash }` | 四类各自的 `{ state, relPath, blocks, syncedAt }` |
| `notes.sync` | `{ bookHash, kinds? }` | `{ written, skipped, conflicts }` |
| `notes.preview` | `{ bookHash, kind }` | `{ markdown }`（不写盘，界面用） |
| `notes.build` | `{ bookHash, kind }` | 生成 relations / map（要 AI，`timeoutMs` 单独给） |
| `profile.get` | `{ bookHash }` | 画像 json（没有就现算） |
| `thread.list` | — | 候选主题 + 已立主题 |

### 新增落盘台账

### settings 新键

加在 `DEFAULT_SETTINGS`（`lib/store.js:92`）与 `mergeSettings` 的严格校验里：

```
obsidianVault      : ''      // 绝对路径，空 = 未配置
obsidianSubdir     : 'dsh-reading'
obsidianAutoWrite  : true
obsidianBackup     : true
readerProfile      : true    // 是否用画像个性化
```

严格校验按现有风格：`obsidianVault` 必须是绝对路径且存在；`obsidianSubdir` 只允许单层目录名（不含 `/`、`..`）。

## 十二、风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 用户在 Obsidian 里手改笔记，被同步覆盖 | 丢他的字，最不可接受 | 锚块协议 + hash 检测 + 备份（§3/§4） |
| 画像过度解读 | 笔记写得不像他要的 | 界面显示真实数字；可一键关掉；`focus` 双窗口取并集 |
| 自动写回把 qa 记录写得很像日志 | 笔记变流水账 | L0 只写「问 + 答摘要 + 关联原句」，不写 prompt、不写模型名；完整问答留在书库里 |
| vault 路径配错，写进别人的目录 | 污染别人的库 | `assertInside` + 只认 `obsidian.json` 里登记过的路径（手选时二次确认） |
| AI 抽人物关系时编关系 | 图是错的，比没有更糟 | 每条边必须带原句，原句核不上就丢掉这条边（沿用 `verifyChapterQuotes` 的 indexOf 核对思路） |
| 书多了笔记散 | 找不到 | `_索引/我的阅读.md` 做总表，每次同步顺带更新一行 |

## 十三、和 `docs/23` 的关系

`docs/23` 里的 Obsidian 适配器（P4）只写了「单向写读书卡 + 蒸馏稿」0.5 天。本文把它扩成四类产物 + 锚块协议 + 回流，
工作量从 0.5 天变成 4.5 天，但 **适配器形状不变**：`lib/bridges/obsidian.js` 仍然是那几个函数，
只是 `write()` 内部从「复制文件」升级成「调 `notesync`」。
`docs/23` 的 P0–P3（Zotero / KOReader / Calibre）不受影响，仍然是独立的一条线。

## 十四、开工前要用户拍板的三件事

1. **默认自动写回要不要开？** 设计里默认 `true`（那条视频的效果靠它），但这是往他的库里写东西，需要他点头。
2. **四类笔记的文件名与目录名认不认？** 定了之后改名会让下次同步重建文件（旧文件留在 `.history`，不删）。
3. **「我现在的判断」这一格留空**——确认他接受「AI 不替你下判断」。
