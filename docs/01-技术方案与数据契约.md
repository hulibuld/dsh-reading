# dsh-Reading 技术方案与数据契约 v1.0

> 状态：待评审
> 适用范围：电脑端 dsh 插件 + 手机端 Android APK + 两者共享的 WebDAV 数据契约
> 一句话立场：**两端共享的是一份可执行的一致性规范，不是一份文档。** 只写文档的契约必然在第三个月失效。

## 0. 结论摘要

| # | 决定 | 性质 |
|---|---|---|
| D1 | CFI 是唯一锚点，但**只信它的后半段**；OPF 前缀每次本地重算，不信任存储值 | 硬规则 |
| D2 | CFI 从**文件字节**推导，不从渲染中的实时 DOM 推导；实时 DOM 只负责「选区→结构坐标」和「结构坐标→可视范围」 | 硬规则 |
| D3 | 标注渲染**禁止改动正文 DOM**（只允许绝对定位覆盖层）。这条直接消灭「加完高亮锚点就漂」这一类 bug | 硬规则 |
| D4 | **三层校验 + 三档处置**：L1 语法 / L2 语义 / L3 内容指纹逐层过；失败→隔离舱，轻微漂移→降级渲染并标记，正常→正常。**任何情况都不删除用户数据** | 硬规则 |
| D5 | MOBI / TXT 在**导入时**确定性转换为 EPUB，此后全系统只认 EPUB。手机端不为这两种格式写第二套锚点 | 架构 |
| D6 | 标注与问答**按记录合并**，不做整文件后写胜；删除用墓碑 | 架构 |
| D7 | 电脑端 WebDAV 走**插件宿主侧**（Node）发请求，不走浏览器。绕过 CORS，这是能不能用的分界线 | 架构 |
| D8 | 电脑端直接复用 foliate-js 全套（解析 + CFI + 渲染 + 覆盖层），只包一层 React；不自研分页器 | 选型 |
| D9 | 手机端用 `flutter_readium` 渲染，但**CFI 编解码由我们自己写**，Readium 只提供「选区→(cssSelector, 文本节点序号, 字符偏移)」和「渲染高亮」两件事 | 选型 |
| D10 | 每本书 = 一个独立 AI 会话空间；主会话只收摘要。防剧透靠**取不到**，不靠提示词 | 架构 |

第 9 条是全局最大风险，见 §10.1，必须在 Phase 0 用 spike 证伪或证实，否则整个锚点策略要换轨。

## 1. 边界与不变量

**不变量（任何实现都不得违反）**

1. 一个锚点 = 一个 EPUB 内的位置，用 CFI 表达。不存在「百分比锚点」「章节+段落锚点」作为**存储主键**。降级定位只能作为**渲染兜底**出现在运行时，不落盘替代原锚点。
2. 同一本书的同一份字节，在所有端上必须产生完全相同的 CFI。这是纯函数要求，不是「尽量一致」。
3. 用户数据只增不删（逻辑删除用墓碑）。任何同步、修复、迁移流程都不得物理丢弃记录。
4. 未解析成功的锚点不得参与渲染。
5. AI 在结构上无法读取阅读位置之后的内容。

**非目标（v1 明确不做）**

- 官方云存储、账号体系、多人协作、书城、推荐、社交流。
- 全本 AI 通读摘要。
- 自动合并冲突（只做逐记录取新 + 历史留档）。
- 手机端 AI 功能。
- PDF 阅读（v2 议题，CFI 不适用于 PDF，需要另一套定位模型，不要在 v1 里预留半成品）。

## 2. 数据契约

### 2.1 WebDAV 目录布局

```
<用户配置的根路径>/
└── dsh-reading/
    ├── library.json                    # 可选：书籍清单索引（可重建，非权威）
    └── books/
        └── <bookHash12>/               # sha256(book file bytes) 前 12 位小写 hex
            ├── meta.json
            ├── progress.json
            ├── annotations.jsonl
            ├── qa.jsonl
            ├── quarantine.jsonl        # 解析失败/结构损坏的记录，只写不读
            ├── book.epub               # 可选；用户选择「书籍也走同步」时存在
            └── history/
                └── <iso8601>__<deviceId>__<filename>
```

**文件夹名用内容哈希，不用书名 slug。** 理由：书名会改、含非 ASCII 与 `/`、大小写在不同 WebDAV 后端行为不一致。slug 只写进 `meta.json` 给人看。

`bookHash12` 是全书字节的 sha256 前 12 位。它同时承担「这本书是不是同一本」的判定职责——哈希不同就是不同的书，不做部分匹配、不做模糊合并。

### 2.2 记录通用信封

`annotations.jsonl` 与 `qa.jsonl` 每行是一个独立 JSON 对象，互不依赖，允许乱序，允许重复 id（读取时按 2.10 合并）。

通用字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schema` | string | 是 | 固定 `"dsh-reading/1"`，用于未来迁移 |
| `id` | string(ULID) | 是 | 单调可排序；同一 `id` 的多次写入取 `updatedAt` 最新 |
| `type` | string | 是 | 见各记录 |
| `createdAt` | string(ISO8601 UTC, 毫秒) | 是 | 创建时刻，写入后不变 |
| `updatedAt` | string(ISO8601 UTC, 毫秒) | 是 | 任何字段变更都要更新 |
| `deviceId` | string | 是 | 产生这条记录的设备；格式 `os-shortid`，如 `mac-7f3a91` |
| `deleted` | boolean | 否 | 墓碑标记。缺省 `false`。为 `true` 时只保留 `id/updatedAt/deviceId`，其余字段可缺 |

### 2.3 meta.json

```json
{
  "schema": "dsh-reading/1",
  "bookHash": "<sha256 hex 全量 64 位>",
  "title": "…",
  "author": "…",
  "language": "zh",
  "format": "epub",            // epub | mobi-converted | txt-converted
  "sourceFormat": "mobi",      // 原始导入格式
  "converterVersion": "1",     // 归一化转换器版本；变更即视为不同书
  "totalChars": 213000,
  "chapterCount": 42,
  "toc": [ { "label": "第一章", "href": "text/ch1.xhtml", "depth": 0 } ],
  "spine": [ { "index": 0, "href": "text/ch1.xhtml", "linear": true } ],
  "createdAt": "2026-10-20T12:00:00.000Z",
  "createdBy": "mac-7f3a91",
  "coverHref": "images/cover.jpg"
}
```

`spine` 冗余存储是刻意的：它让手机端在不解析 OPF 的情况下也能做 CFI 前缀校验与重建。

### 2.4 progress.json

```json
{
  "schema": "dsh-reading/1",
  "cfi": "epubcfi(/6/4[ch1]!/4/2/2/1:0)",
  "chapterHref": "text/ch1.xhtml",
  "chapterProgression": 0.42,
  "bookProgression": 0.07,
  "updatedAt": "2026-10-20T12:34:56.789Z",
  "deviceId": "mac-7f3a91"
}
```

`cfi` 是权威位置；`chapterHref` + 两个 progression 只是降级渲染用的冗余。`bookProgression` 用于进度条显示，不用于定位。

### 2.5 annotations.jsonl

```json
{"schema":"dsh-reading/1","id":"01JB...","type":"highlight","cfi":"epubcfi(/6/4[ch1]!/4/2/2/1:0,/4/2/2/1:24)","cfiStart":"/4/2/2/1:0","cfiEnd":"/4/2/2/1:24","chapterHref":"text/ch1.xhtml","textExcerpt":"……","color":"yellow","note":"","createdAt":"…","updatedAt":"…","deviceId":"…"}
{"schema":"dsh-reading/1","id":"01JC...","type":"note","cfi":"epubcfi(/6/4[ch2]!/4/6/1:0,/4/6/1:0)","cfiStart":"/4/6/1:0","cfiEnd":"/4/6/1:0","chapterHref":"text/ch2.xhtml","textExcerpt":"","color":"blue","note":"这里和第三章对不上","createdAt":"…","updatedAt":"…","deviceId":"…"}
{"schema":"dsh-reading/1","id":"01JD...","type":"bookmark","cfi":"epubcfi(/6/8[ch3]!/4/2/1:0)","chapterHref":"text/ch3.xhtml","label":"读到一半","createdAt":"…","updatedAt":"…","deviceId":"…"}
```

字段规则：

- `type`：`highlight` | `note` | `bookmark`。
- `cfi`：完整 CFI 字符串（含 `epubcfi(...)` 包裹）。范围型标注用 `buildRange` 形式；点锚点用单个路径。
- `cfiStart` / `cfiEnd`：**去掉前缀的右半段**，即与 Readium `partialCfi` 同构。冗余存储的目的：前缀漂移时可以只重建前缀、保留内容位置。范围型必填两者；点锚点只填 `cfiStart`。
- `chapterHref`：spine 中的 href，用于前缀重建与降级定位。
- `textExcerpt`：选中原文，**原样保存不做 trim**（空白参与字符偏移），上限 512 字符，超出截断并在 `textExcerptTruncated` 置 `true`。
- `textFingerprint`：`{ "head": 前 48 字符, "tail": 后 32 字符, "len": 原文长度, "hash": sha256(原文 collapse 空白后) }`。用于锚点漂移判定。
- `color`：`yellow|green|blue|pink|purple`，五色枚举，不接受任意值。`note` 类型必须带 `color`。
- `note`：纯文本，允许换行，上限 8 KB。
- `label`：仅 `bookmark` 使用。

### 2.6 qa.jsonl

```json
{"schema":"dsh-reading/1","id":"01JE...","anchorCfiRange":"epubcfi(/6/4[ch1]!/4/2/2/1:0,/4/2/2/1:24)","anchorAnnotationId":"01JB...","question":"……","answer":"……","contextExcerpt":"……","contextCfiRange":"…","cutoffCfi":"epubcfi(/6/4[ch1]!/4/2/2/1:0)","model":"deepseek-v4.1-flash","threadId":"01JF...","parentId":"01JE-previous","createdAt":"…","updatedAt":"…","deviceId":"…"}
```

- `anchorCfiRange` **必填**。没有锚定的回答不落盘——这条在写入函数里做硬校验，不是靠调用方自觉。
- `anchorAnnotationId`：如果问题是由某条划线触发，填它的 id；此时 `anchorCfiRange` 必须与那条划线一致，不一致视为数据损坏。
- `cutoffCfi`：提问时刻的阅读位置。**它同时是审计证据**：事后可以验证这条回答没看过 cutoff 之后的内容。
- `contextExcerpt`：真正喂给模型的原文片段，原样存。用于复盘「模型答错是因为喂错了，还是因为没想到」。
- `parentId`：追问时指向上一条 qa 的 id，形成链。`threadId` 标识整条对话线。
- `answer` 允许 Markdown。

### 2.7 quarantine.jsonl

与 annotations 同结构，额外字段：

```json
{"schema":"dsh-reading/1","id":"…","type":"highlight","reason":"cfi_parse_failed","rawCfi":"epubcfi(/6/4[ch1]!/4/2/2/1:0,/4/2/2/1:XX)","sourceDeviceId":"…","ingestedAt":"…","repairable":false}
```

`reason` 枚举：`cfi_parse_failed` | `cfi_prefix_mismatch` | `fingerprint_drift` | `schema_invalid` | `orphan_anchor`。

**隔离舱只写不读。** 阅读器永不渲染其中的记录。它存在的意义是：数据还在，等以后能修。给用户一个只读界面能看到「有 3 条标注暂时无法定位」，并提供「导出」按钮。

### 2.8 history/

写入前的旧版本整文件副本，命名 `<原文件名>.<iso8601>.<deviceId>`。仅在**覆盖写**发生前保存，保留最近 20 份，超出按时间删最旧。

`history/` 不是备份方案，是取证材料。真正的防丢靠 §2.10 的合并，不靠历史。

### 2.9 锚点校验：三层 + 三档处置

> **v1.1 修订**：原方案只做「语法层校验」，实测发现不够。详见 `docs/03-CFI实测报告.md` §三。
> foliate-js 的 `parse()` 对畸形输入异常宽容 —— `epubcfi(/4/2,/1:8,/1:3)`（起止倒置）与
> `epubcfi(/6/4!/4/2[p1],/1:3,/1:5)`（跨文档）都能解析成功，`toRange()` 也不抛异常，
> 但返回的 Range 语义完全错误。只用 try/catch 挡不住它们。

**校验必须分三层，逐层递进：**

| 层 | 检查内容 | 失败 → quarantine.reason |
|---|---|---|
| L1 语法 | `CFI.parse()` 不抛异常；恰好一个 `!` 分隔符 | `cfi_parse_failed` |
| L2 语义 | `CFI.toRange()` 不抛异常；返回 Range 非 null；`startOffset <= endOffset`；区间不跨文档 | `cfi_resolve_failed` / `cfi_range_inverted` / `cfi_cross_document` / `cfi_offset_out_of_bounds` |
| L3 内容 | 从 Range 取出的文本经 `textFingerprint` 算法计算后，与记录中 `textFingerprint` 一致 | `fingerprint_drift` |

**L3 是必需的，不是锦上添花。** 它是唯一能挡住 L1/L2 都放行的静默失败的机制。这直接决定了
`textExcerpt` 与 `textFingerprint` 在 schema 中必须是**必填字段**——没有指纹就无法做 L3 校验，
没有 L3 校验就无法区分「锚点是对的」和「锚点看起来对但指向别处」。

额外的机械判畸规则（在 L1 之前先跑，成本低）：

1. `cfiStart` 缺失 / 为空串 / 指向文档根节点 → 直接隔离（Readest 空起始 CFI 教训）
2. `type === "highlight"` 但解析出的 Range `collapsed === true` → 隔离（`cfi_collapsed_highlight`），高亮不应零宽
3. 区间跨多个文档（`!` 两侧 href 不一致，或 local path 越界）→ 隔离（`cfi_cross_document`）

**三档处置（在三层校验之后）：**

| 档 | 条件 | 行为 |
|---|---|---|
| A 正常 | L1/L2/L3 全通过，且前缀与本地 OPF 推导一致 | 正常渲染，`anchorStatus: "ok"` |
| B 可修 | L1/L2/L3 全通过，但前缀不一致或指纹轻微漂移（差异在容差内） | **就地重建前缀**写回；渲染时叠加「位置可能偏移」提示；记录 `anchorStatus: "repaired"` 或 `"drifted"` |
| C 隔离 | 任一层失败 | 移入 quarantine，不渲染，计入待修复计数，`anchorStatus: "quarantined"` |

判定中的「前缀一致」定义为：CFI 里 `!` 之前的 spine 索引解析出的 href，等于记录里的 `chapterHref`。

**关键约束：隔离不等于删除。** 档 C 的记录进入 `quarantine.jsonl`（只写不读），
原始记录完整保留在 `rawRecord` 字段里，用户可在「待修复」面板里看到并手工处理。
这是对「畸形 CFI 丢弃优先」的精确实现——**丢弃的是「拿去渲染」这个动作，不是用户数据本身**。
原方案 §10.2 已指出该字面冲突，这里给出落地方式。

**为什么 L3 用指纹而不是原文精确比对：**

原文会因重新排版、字体替换、软连字符规范化而变化，精确比对的假阳性过高。
指纹取 `head(48) + tail(32) + len + sha256`，抗局部改动、允许中间区段漂移，
既能挡住「指向完全不同的段落」（B6 类），又能容忍「同段落有细微差异」。

### 2.9.1 实现提醒：`oneOf` 的报错信息不能用

用 `ajv` 实测时发现：顶层用 `oneOf` 分发 7 种记录类型，当某个字段缺失（比如 highlight 缺 `textFingerprint`）时，`ajv` 会报告**所有 7 个分支**的缺失字段，其中包含 meta 分支的 `bookHash` / `title`。用户和开发者看到的第一个错误往往是无关的。

这不是 schema 错误，是 `oneOf` 的固有行为。但直接影响可用性 —— 契约校验失败时的报错必须能定位问题。

**实现要求**：

1. `validate()` 包装函数必须先按 `type` 字段选分支，只校验该分支的 `$defs`，不跑顶层 `oneOf`。顶层 `oneOf` 只用于「类型未知」的兜底。
2. 报错信息按分支过滤：只保留与 `type` 匹配的 `instancePath` 前缀。
3. 校验失败的错误要带上具体字段路径（`annotations[3].textFingerprint`），不能只给「校验失败」。

这条看起来是小事，但它决定了 P3 同步排障时能不能一眼看出是哪条记录哪个字段坏了。

### 2.10 冲突与合并

**progress.json：时间戳后写胜。**

- 比较 `updatedAt`；相等时比较 `deviceId` 字典序（保证两端结果一致，避免来回翻转）。
- 写入前把旧文件复制进 `history/`。
- 若检测到双方 `updatedAt` 相差超过 24 小时且方向反常（更新的那条 `deviceId` 不是本机却比本机旧），不覆盖，保留旧值并进入 `conflict` 状态，下次同步带 `force` 才写。

**annotations.jsonl / qa.jsonl：按 id 逐条合并，不做整文件后写胜。**

合并算法（两端必须实现同一份，并纳入一致性测试）：

```
1. 读远端文件 → 逐行 JSON.parse，失败行 → quarantine，继续
2. 读本地记录集 → 同样处理
3. 按 id 分组
4. 每组内按 (updatedAt, deviceId) 降序取第一条为胜出
5. 胜出记录 deleted=true 的，从渲染集中移除，但保留在文件中（墓碑）
6. 输出排序：先按 createdAt 升序，再按 id 升序 —— 保证写回后字节稳定
```

关键点：**增量是加法语义。** 两台设备各加一条划线，合并后两条都在。原方案里「整文件后写胜」会把其中一台的划线直接抹掉，这对标注类是数据丢失，不可接受。

墓碑的保留期：永久。体积上每条墓碑约 120 字节，一万条标注量级下完全可忽略。

**meta.json：** 后写胜，但 `bookHash` 不一致视为灾难，不上传、不覆盖，报「同一目录出现两本不同的书」。

### 2.11 同步流程与并发控制

```
pull → merge(local, remote) → 检测差异 → push(合并结果) → 更新 lastSyncedAt
```

并发保护优先级（逐级降级，按后端能力自动探测）：

1. `If-Match: <ETag>` 条件 PUT（Nutstore 支持则用这条）
2. `LOCK` / `UNLOCK` 文件锁，TTL 60s
3. 无保护：读-改-写 + 写前再读一次比对 ETag（窄窗口，接受）

维护 `<root>/dsh-reading/.sync-state.json` 记录每设备 `lastSyncedAt` 与上次见到的 ETag，用于快速跳过无变化文件（PROPFIND 比 GET 便宜得多）。

后台触发时机（借 KOReader highlightsync 的经验）：阅读器**关闭/切后台**、**每 5 分钟**（仅当有未同步记录）、**手动点同步**。不做逐字符实时同步。

## 3. CFI 规则（规范性）

这一节是契约里唯一不可协商的部分。两端实现必须逐条对上。

### 3.1 为什么不能信任存储的 CFI

一个完整 CFI 是 `epubcfi(/6/4[ch1]!/4/2/2/1:0)`，分两段：

- **前缀** `/6/4[ch1]`：指向 OPF 里的 spine itemref。这依赖「OPF 作为 XML 文档，其子元素如何编号」。
- **后缀** `!/4/2/2/1:0`：指向该 XHTML 内部节点。依赖「XHTML 作为 DOM，其子节点如何编号」。

两段都依赖解析器的编号规则。只要两端实现细节有一处不同，锚点就整体错位——而且是**静默错位**，看起来正常渲染，实际高亮跑到了别的段落。Readest 的错位事故就是这条链路两端判定不一致。

对策不是「写得更仔细」，是**把不确定性逐段消除**：

- 前缀：不信任，每次由本地解析的 OPF 重算。`chapterHref` 是更可信的键。
- 后缀：必须由两个端实现**同一套规范化算法**，并用同一批测试向量强制对齐。

### 3.2 规范化树算法（必须逐字实现）

对任意 XML/HTML 文档，定义其「CFI 子节点索引」如下。这与 EPUB CFI 规范 §"Step Reference to Child Element or Character Data" 一致，且与 foliate-js `epubcfi.js` 的 `indexChildNodes` 实现一致（`/tmp/foliate-probe/epubcfi.js:186-231`）。

```
isTextNode(n)    = n.nodeType ∈ {3, 4}     // Text, CDATA
isElementNode(n) = n.nodeType == 1         // Element

getChildNodes(node):
  取 node.childNodes，只保留 isTextNode 或 isElementNode 的
  // 注释、处理指令、DOCTYPE 全部忽略 —— 规范原文 "content other than element
  // and character data is ignored"

indexChildNodes(node) 返回数组 arr：
  a) 按文档顺序遍历 getChildNodes(node)，折叠成「元素与文本块交替」的列表：
     - 首项是元素 → 压入哨兵 'first'
     - 连续的多个文本节点合并为一个块（多个节点 → 一个数组）
     - 两个元素相邻时，中间插入 null（表示此处存在一个空文本块）
     - 末项是元素 → 压入哨兵 'last'
  b) 数组首部 unshift 'before'，对应索引 0
  c) 数组尾部 push 'after'
```

结果索引布局固定为：`0=before, 1=第一个子节点, 2=第二个, …, n+1=after`。因此**偶数索引是元素，奇数索引是文本块**（规范如此，不是巧合）。

**三条由该算法直接推出的硬性推论：**

1. **相邻文本节点被合并成一个逻辑块，偏移跨节点累加。** 这是锚点稳定的根基：任何一次「把文本节点切成两半」的操作（高亮包裹、语法着色、批注标记）都**不会**改变 CFI。前提是这些操作发生在 $3.4 允许的位置。
2. 空元素（`<br>`、`<img>`、`<hr>`）与相邻元素之间会插入 `null` 占位，索引因此跳号。两端必须都实现这个占位，否则从该处往后全部错一位。
3. `before`(0) 与 `after`(n+1) 是虚拟索引，实现必须能返回，不能当越界报错。

### 3.3 生成与解析

**生成（选区 → CFI）**

```
selection (live DOM Range)
  → 取 startContainer/startOffset, endContainer/endOffset
  → 沿规范化树向上走父链，收集每层的 (index, offset)
     · offset 必须换算到合并后的文本块坐标（跨节点累加）
  → spine 部分：由该文档在 OPF spine 中的序号本地推导
  → buildRange([start], [end]) → 完整 CFI 字符串
```

**解析（CFI → 可视范围）**

```
parse(cfi)
  → 校验：必须含恰好一个 '!'；range 必须两端齐全；任一端空/缺 → 抛错（走 §2.9 档 C）
  → 前缀：解析出 spine 序号 → 查本地 spine 表得 href
     · 若记录带 chapterHref 且与推导结果不符 → 以 chapterHref 为准重建前缀（档 B）
  → 后缀：collapse 出 start / end 两段 parts
  → 沿规范化树下降，得到 (node, offset) 或 (node, before/after)
  → 在实时 DOM 上转成 Range
```

### 3.4 禁止事项（违反即视为锚点污染）

1. **不得**在正文流内容中插入、删除、移动任何元素或文本节点。高亮、笔记标记、书签图标全部用绝对定位覆盖层绘制。
   - 参考实现：foliate-js `overlayer.js` 用 `getClientRects()` 计算文本片段矩形，在覆盖层上画背景色，正文 DOM 一动不动。
   - 如果某天确实需要内联元素（例如脚注角标），只能由**内容源**提供，且必须写进 `converterVersion`，变更即视为新书。
   - **实测证据**（`docs/03-CFI实测报告.md` §五）：`<p>abcdef</p>` 与 `<p>abc<i></i>def</p>` 文本内容完全相同，但 CFI 偏移基准不同。插一个空元素就能让整章锚点集体偏移。这不是风格偏好，是数据完整性。
2. **不得**在计算偏移前 trim / collapse 空白。字符偏移作用于原始字符数据。
3. **不得**使用 `id` 断言（CFI 里的 `[ch1]` 形式）作为唯一识别手段。可写入（便于人类阅读），但解析时只作校验提示，不作导航依据。
   - 实测补充：`id` 断言的优先级**高于**索引——`epubcfi(/4/2/2[B])` 中索引指向 A，但断言 `[B]` 生效，仍解析到 B。这既是抗重排的保险，也是「索引错却静默成功」的来源。所以 L3 内容层校验不可省（§2.9）。
4. **不得**用 `innerHTML` 重建正文后再复用旧 CFI。重建即新树。
5. **不得**让书内脚本运行。`<iframe sandbox="allow-same-origin">`（**去掉 `allow-scripts`**）+ CSP `script-src 'none'`。EPUB 规范允许脚本，这是安全面，不是可选项。
6. **不得**在调用 CFI 生成/解析函数时不传 filter。见 §3.4.1。
7. **不得**在 CFI 路径的中间段写 `id` 断言。断言只允许出现在**每条 local path 的最后一段**。

### 3.4.1 filter 是强制参数，不是可选项

实测（`docs/03-CFI实测报告.md` §二）：同一个选区，注入一层高亮 `<span>` 后——

```
不传 filter：epubcfi(/4/2[h],/1:3,/2/1:3)   ← 被注入节点污染，多一层 /2/1
传 filter：  epubcfi(/4/2[h],/1:3,/1:8)     ← 与未注入时完全一致
```

更危险的是反向：用「干净 CFI」去解析一个已注入 DOM 的文档，不传 filter 会抛
`Offset out of bound`；而如果注入位置恰好没跨过偏移，它**不报错**，只是把高亮画到别处。

**实现约束**：

- `core/cfi.ts` 的所有导出函数（`fromRange` / `toRange` / `fromElements` / `toElement`）内部**强制**注入统一 filter，不对外暴露无 filter 的调用路径。API 层面就不给出错的机会。
- 统一 filter 的语义：对项目自己注入的所有节点（覆盖层、选择手柄、调试标记）返回 `FILTER_SKIP`，其余返回 `FILTER_ACCEPT`。识别依据是 `data-dsh-reading-injected` 属性，不靠 class 名猜。
- `FILTER_SKIP` 会被 `getChildNodes` 展平递归（子节点上浮一层）；`FILTER_REJECT` 会整棵子树消失。两者语义不同，不要混用。
- 手机端 Dart 实现必须做同一件事，filter 行为纳入 golden 向量（至少在 `adjacent-text` 与 `nested-inline` 两个 fixture 上各有一条带注入的向量）。

### 3.4.2 断言位置的硬规则

实测：`partsToNode` 只读 `parts[parts.length - 1].id`。所以

```
epubcfi(/4/2[B]/2[p1],/1:0)   →  抛 Cannot read properties of undefined
```

中间段的断言不仅不生效，还会让解析路径断掉。生成时若沿父链逐层收集 id，很容易写出这种 CFI。

**规则**：生成函数在组装 parts 时，只保留最后一段的 `id`，其余层的 `id` 置空。解析函数遇到中间段带 `id` 的输入，直接判 L2 失败进隔离（不做「宽容忽略」，因为那是别人实现差异导致的，我们无从判断其意图）。

### 3.5 字符偏移的编码单位

统一为 **UTF-16 code unit** 计数，与 DOM `Range.offset` 和 JS `String.length` 天然一致。Dart 的 `String` 同样是 UTF-16，所以手机端不需要转换。

这一条必须写死在契约里：若哪天引入 Python/Go/Rust 端，它们默认按 code point 或字节计数，会整体错位。测试向量里要含 emoji 与 CJK 扩展 B 区字符。

### 3.6 一致性测试向量（golden vectors）

`golden/` 目录是契约的可执行部分，结构：

```
golden/
├── fixtures/                     # 构造出来的刁钻 EPUB
│   ├── nested-inline.epub        # <em><strong> 深嵌
│   ├── adjacent-text.epub        # 相邻文本节点（实体引用会制造这种结构）
│   ├── empty-elements.epub       # <br> <img> <hr> 连排
│   ├── cdata.epub
│   ├── ruby-rt.epub              # 注音，嵌套极深
│   ├── rtl.epub
│   ├── footnote-refs.epub
│   └── emoji-cjk-b.epub          # 代理对与扩展区
├── vectors.json                  # { fixture, chapterHref, startPath, startOffset,
│                                 #   endPath, endOffset, expectedCfi, excerpt }
└── run.mjs / run.dart            # 两端各自的 runner，输出 diff
```

**Phase 0 的验收线：TS 与 Dart 两个实现跑同一批向量，逐条字节级相等，0 差异。** 不达标不许开工 UI。

这也是「两端共享数据契约」这句话的真实含义：共享的是测试向量和算法描述，不是运行时。

## 4. 格式归一化（MOBI / TXT → EPUB）

### 4.1 为什么必须转换

CFI 是 EPUB 的定位语法，MOBI 和 TXT 根本没有「文档内部节点路径」这个概念。原方案要求两端都能直接读 mobi/txt，同时要求锚点统一用 CFI——这两个要求在工程上不相容。

出路只有一条：**把非 EPUB 格式在导入时就变成 EPUB，此后全系统只认 EPUB。**

### 4.2 转换规则

- **MOBI / AZW3**：解析出 HTML 内容 + 目录 + 元数据，打包成最小合规 EPUB3（`mimetype`、`META-INF/container.xml`、`content.opf`、每章一个 XHTML）。不追求还原原版排版，只追求结构稳定。
- **TXT**：按固定规则切章（`^\s*(第[一二三四五六七八九十百千零〇]+[章节回卷篇]|Chapter\s+\d+|CHAPTER\s+[IVXLC]+)`，可配置），编码探测顺序 UTF-8 → GB18030 → UTF-16LE/BE（带 BOM 优先），每章一个 XHTML，段落按空行/换行切 `<p>`。

### 4.3 确定性要求（关键）

同一份输入字节 + 同一 `converterVersion`，必须产出**逐字节相同**的 EPUB。因此：

- 禁止写入时间戳、随机 UUID、本机路径到 EPUB 内部。
- ZIP 条目顺序固定、压缩级别固定、mtime 统一置零。
- 若转换器算法有任何改动，`converterVersion` +1，`bookHash` 随之变化 —— **旧书的标注不会自动迁移到新哈希下**。这是刻意选择：宁可让用户重新导入，也不做可能错位的静默迁移。

### 4.4 分工

| 端 | EPUB | MOBI | TXT |
|---|---|---|---|
| 电脑端 | 直接读 | 导入时转换 | 导入时转换 |
| 手机端 | 直接读 | v1 不支持导入（可读已同步的转换产物） | 同左 |

手机端不实现转换器，是这个方案里最省事的一刀。用户若只有手机，让他用电脑转一次、或者干脆先只支持 EPUB。这个限制要写在设置页上，不要藏。

## 7. 技术选型

### 7.1 电脑端

| 层 | 选择 | 理由 / 代价 |
|---|---|---|
| EPUB 解析 | **foliate-js `epub.js`**（vendor 到固定 commit） | 已验证：无运行时依赖、纯 ESM、MIT。同时处理 EPUB2/3、加密探测、导航 |
| CFI | **foliate-js `epubcfi.js`** | 与 §3.2 完全一致（这节的算法就是照它写的）。导出 `parse/toString/collapse/fromRange/toRange/fromElements/toElement/isCFI/compare` |
| MOBI 解析 | **foliate-js `mobi.js`** | 转成与 EPUB 相同的 book 对象，转换器直接复用 |
| 渲染 | **foliate-js `paginator.js` + `overlayer.js`** | 分页、双栏、选区、覆盖层高亮一体解决。代价：自带 iframe 边界（见 §10.4） |
| 框架 | React（dsh client 侧既有栈） | 不引入第二套 |
| WebDAV | **npm `webdav` v5**（host 侧） | 支持 `If-Match`、`PROPFIND`、`MKCOL`、流式 PUT |
| 配置 | dsh 插件的 Schemastery `Config` | 与宿主一致，不另造配置系统 |
| 凭据 | 系统钥匙串（macOS Keychain / Windows Credential Manager） | 绝不写进明文配置文件 |

**foliate-js 是 0.0.0、无 release、README 自述 API 会说变就变。** 因此必须 vendor（复制进仓库）而非 npm 依赖，锁 commit，并把它包在一个自己的 `FoliateView` 接口后面——将来换实现只改这一层。

### 7.2 手机端

| 层 | 选择 | 理由 / 代价 |
|---|---|---|
| 阅读渲染 | **`flutter_readium` 0.7.x** | Readium 官方 kotlin-toolkit 绑定；分页/主题/高亮 decorations/进度恢复/目录/搜索都是现成的。0.x 但更新极快（5 个月 0.0.1→0.7.0），publisher 是丹麦盲人图书馆，不是野包 |
| CFI | **自写 Dart 实现** | Readium 不给 CFI，只给 Locator。契约要求 CFI，所以必须自己算。这是本方案最大工作量点之一 |
| WebDAV | **`webdav_client_plus` 3.x** | 支持条件写、锁、流式、取消。条件写是多端同步的前提 |
| 本地库 | **drift**（SQLite） | 类型安全、可测试、支持复杂查询（按书/按章节/按颜色筛标注） |
| 凭据 | **flutter_secure_storage** | Android Keystore 后端 |
| 状态 | Riverpod | 轻、可测 |

**不选 `epub_viewer_pro` / `advanced_epub_reader` / `vocsy_epub_viewer` 的原因：** 它们全部以 HTML 或原生黑盒方式渲染，锚点粒度只能到「章节 + 滚动位置」，做不了字符级范围。用户原方案里「手机端可直接用这些包覆盖高亮」的判断在锚点这一项上不成立。高亮本身不是难点（按字符区间切 `TextSpan` 几十行就够），难点是**分页导致的偏移不稳定**和**跨端锚点一致**，这两件事这些包都不解决。

### 7.3 两端共用的工具

| 用途 | 方案 |
|---|---|
| 契约校验 | JSON Schema Draft 2020-12，`docs/schema/contract.schema.json` 单一文件承载全部记录类型 |
| 一致性 | `golden/vectors.json` + 两个 runner |
| 版本 | 契约版本走 `schema` 字段 + `converterVersion` 字段，两个独立演进 |

## 8. AI 子系统

### 8.1 防剧透：靠取不到，不靠提示词

唯一取文入口是 `host/ai/scoped-context.js`，函数签名：

```js
getContext({ bookId, cutoffCfi, targetRange, before = 1, after = 1 })
// 返回 { paragraphs: [{cfiRange, text, isTarget}], truncated: bool, cutoffReachedAt: cfi }
```

它做三件事：

1. 把 `cutoffCfi` 解析成「spine 内字节位置」；
2. 用 CFI **只取** `cutoffCfi` 之前的节点；
3. 若 `targetRange` 完全在 cutoff 之后，直接抛错——这种情况在 UI 上根本不该出现，出现即说明锚点坏了。

模型拿到的 prompt 里只有这段已读文本。**它没有别的取文工具**。子会话的工具白名单只允许 `reading_get_context`，而这个工具自己会再裁一次。双保险的意义：即便提示词被绕过、即便模型主动要「整章」，它拿到的仍是截断后的内容。

`cutoffCfi` 唯一来源是 `progress.json.cfi`，不让调用方传。这样「模型看见什么」与「用户读到哪」在代码里是同一条事实。

### 8.2 子会话隔离

- 每本书一个 `threadId`，同书的追问复用它，跨书不共享。
- 每次提问派生一个短生命周期子会话：喂进 `contextExcerpt` + 章节大纲 + 阅读位置摘要，拿回答案。
- **主会话只收一条摘要事件**：`{book, question, answerPreview, anchorCfi}`。主会话上下文里永远没有整章原文。
- 子会话结束即销毁。持久化的是 `qa.jsonl`，不是会话记录。

### 8.3 让模型知道用户在哪

每次提问自动附带的结构化上下文（不是让用户口述）：

```
《书名》 作者
当前：第 3 章《…》 / 第 2 节
已读范围：至第 3 章 42%（CFI: …）
本次选区：第 3 章 第 2 节，第 14 段（属于已读范围）
```

这对应 dsh-plugin-handout 的 `handout_goto` 思路：位置是状态，显式告知，不靠猜。

### 8.4 回答锚定强制

`qa.jsonl` 的写入函数首行校验 `anchorCfiRange` 非空且可解析。不满足直接 throw，不降级、不落盘。

UI 上每条回答下方有「回原文」按钮，点击滚动到对应范围并短暂闪一下覆盖层。这对应 dsh-paper-reader 和 dsh-deep-reading 的「带位置引用」要求。

### 8.5 跨书记忆

用户可以把某条问答「存入记忆」。实现：写进 dsh 的长期记忆（或一个独立的 `memory.jsonl` 挂在根目录），带 `sourceBook` + `sourceCfiRange` 溯源。跨书可检索，但**必须带出处**——没有出处的思考不入库。

## 9. WebDAV 与 BYOC

### 9.1 支援清单

v1 只做「兼容 WebDAV 协议」的通用接入，页面内提供坚果云的分步指引作为首选示例。其他（Nextcloud、群晖、InfiniCLOUD、自建）走同一套通用表单。

### 9.2 连接测试的分步探测

不做一个笼统的「测试连接」，做四步，逐步给反馈：

```
① DNS/TCP 可达          → 失败：「地址连不上，检查网络或地址拼写」
② PROPFIND 根路径 207   → 失败：401/403 →「认证失败」；404 →「路径不存在」
③ 在目标路径下 MKCOL 试探 → 失败：403 →「没有写入权限」
④ PUT 一个 16 字节探针再 DELETE → 失败：「可以读但不能写，检查应用密码权限」
```

每一步单独显示，用户能看见卡在第几步。这比「连接失败」有用得多。

### 9.3 错误分类（必须穷举，前端按 code 映射文案）

| code | 触发 | 中文提示要点 |
|---|---|---|
| `E_BAD_URL` | 缺 scheme / 非 http(s) | 必须以 `https://` 开头 |
| `E_DNS` | 解析失败 | 地址或网络问题 |
| `E_TLS` | 证书错误 | 系统时间或证书问题 |
| `E_TIMEOUT` | 超时 | 网络慢，或需要代理 |
| `E_AUTH` | 401 | 用户名或应用密码错 |
| `E_MUST_APP_PASSWORD` | 用主密码登录被拒 | 坚果云必须用「应用密码」 |
| `E_FORBIDDEN` | 403 | 路径无权限 |
| `E_NOT_FOUND` | 404 | 路径不存在 |
| `E_NO_WRITE` | PUT 403 | 能读不能写 |
| `E_QUOTA` | 507/413 | 空间不足或单文件超限 |
| `E_RATE_LIMIT` | 429 | 请求太频繁，稍后重试 |
| `E_CORS` | 浏览器侧预检失败 | 仅开发期出现，生产走宿主代理不会有 |

### 9.4 坚果云指引（直接写在页面上）

1. 登录坚果云网页版 → 右上角头像 → **账户信息** → **安全选项**
2. 找到 **第三方应用管理** → 点 **添加应用**
3. 名称填 `dsh-Reading`，生成后**立即复制**那串密码（只显示一次）
4. 地址填 `https://dav.jianguoyun.com/dav/`
5. 用户名填你的坚果云登录邮箱，密码填**上一步生成的应用密码**（不是登录密码）
6. 建议先在网盘里建一个空文件夹 `dsh-reading`，路径填 `/dav/dsh-reading`

第 5 步是绝大多数人卡住的地方，要加粗，最好配一张截图。

### 9.5 频率限制

坚果云对 WebDAV 有请求频率限制（约 600 次/30 分钟量级）。同步引擎必须：

- 用 PROPFIND 拿目录快照，只在 ETag 变化时 GET
- 合并后**一次批量 PUT**，不逐条 PUT
- 失败退避：1s → 4s → 16s → 60s，最多 5 次，之后转手动
- 同步预算计数，逼近上限时降级为「仅同步进度」

这条不做，用户会在读了两小时后发现同步被封。

## 10. 原方案的风险与调整

### 10.1 【最高风险】手机端能否产出与电脑端一致的 CFI —— 尚未证实

**问题**：`flutter_readium` 的 Dart 层不暴露 `partialCfi`（它的 `Locations` 只有 `progression/totalProgression/position/cssSelector/domRange/fragments`）。Readium 规范里的 `partialCfi` 存在于 kotlin-toolkit，但没桥接到 Dart。这意味着手机端拿不到 CFI，只能自己算。

**自算的前提**：能从 Readium 拿到「选区的元素 CSS 选择器 + 文本节点序号 + 字符偏移」。它确实提供 `cssSelector`，但 `domRange` 在 Dart 层被声明成 `String?`，与规范定义的 Object 结构不符，实际内容未知。

**必须先做的 spike（Phase 0，1–2 天）**：
用 `flutter_readium` 打开测试书，选中一段文字，打印出所有可得的位置信息，验证：
1. 能否稳定拿到目标元素与文本偏移；
2. 同一个选区重复选 10 次，拿到的值是否恒定；
3. 字号/屏宽变化后是否恒定；
4. 与电脑端对同一段落算出的 CFI 是否一致。

**如果证伪**，切换 Plan B：存储主锚点改为 **structural anchor**（`chapterHref` + 元素路径 + 字符偏移，本质上是 partialCfi 的自有编码），CFI 降级为电脑端导出/互操作字段。契约 §2.5 的 `cfiStart/cfiEnd` 字段设计已经为此留了位置——它们本身就是右半段。**这不是推倒重来，是换字段语义。** 但必须在 Phase 0 就决定，不能拖到 Phase 5。

### 10.2 「锚点统一用 CFI」与「畸形 CFI 丢弃优先」字面冲突

原方案第 1 条要求锚点统一 CFI，第 2 条要求解析失败就丢弃。但如果解析失败就丢，那用户的划线就没了——这不是「丢弃优先」，是数据丢失。

**调整**：改为隔离舱机制（§2.7 / §2.9）。原则表述改成：**「不可解析的锚点绝不参与渲染，但绝不删除记录。」** 同时把「前缀不可信、本地重算」写进契约——这一条把最容易出问题的那一半不确定性直接消掉了。

### 10.3 整文件后写胜会吃掉另一台设备的标注

原方案「按 updatedAt 后写者胜」对 `progress.json` 是对的，对 `annotations.jsonl` 是错的。两台设备各加一条，后写的把先写的整文件覆盖，先写的那条凭空消失，且 `history/` 里那份用户根本不会去看。

**调整**：progress 用 LWW，annotations/qa 用逐 id 合并 + 墓碑（§2.10）。复杂度增加很小（几十行），但堵住的是数据丢失。

### 10.4 foliate-js 的 iframe 与 dsh 插件约束

dsh 官方插件开发文档明确要求「插件页面渲染成 slot 里的 React 组件，不要从 Host 提供 HTML 页面再 iframe 嵌进去」，理由是 iframe 内的文档拿不到宿主主题 token、明暗切换和 locale。

**已核实的部分**：这条约束的原文针对的是「插件页面」——即插件自己的 UI 不该用 iframe 绕过宿主环境。原始理由是 iframe 拿不到主题 token、明暗切换和 `ctx.locale`，这三样都是**插件 UI** 才需要的。

**我的判断**：书籍内容的渲染视口不是「插件页面」。EPUB 的 CSS 必然会污染宿主样式，宿主样式也必然会破坏书的排版——这是双向需要隔离的场景。而主题 token 与 locale 对书籍正文本来就不该生效（书有它自己的样式表和语言）。所以 iframe 在这里是**工程必要**，不是偷懒。

**但这仍是判断，不是白纸黑字。** 边界在于「视口容器算不算插件页面」。所以：

- 设计上把 foliate 的 iframe 严格限制在 `Reader.tsx` 内部的一个视口容器里，插件 UI（书架、目录、问答面板、设置）全部是原生 React 组件，主题与 locale 正常继承。
- Phase 1 开工前先拿这个理解去问一次（或看 dsh 里现有插件有没有同类先例）。
- 若被否，Plan B：把 foliate 的分页器改成不依赖 iframe，正文挂在 Shadow DOM 里。CSS 隔离仍然成立，但 `contentDocument` 相关代码要全部改写，工作量约 1–2 周。这个 Plan B 会连带影响 `overlayer`（它依赖 iframe 内的 `getClientRects`，Shadow DOM 下也成立，但要改文档引用）。

### 10.5 MOBI / TXT 跨端不可行

见 §4。原方案假设两端都能读三种格式，在 CFI 约束下不成立。调整：导入时转换，手机端只读 EPUB。

这项调整会少一个功能（手机端直接导 mobi），但换来锚点体系的一致性。我倾向于这么换。

### 10.6 flutter_readium 的工具链锁定

它要求 Flutter ≥3.44.8 / Dart ≥3.11 / compileSdk 37 / minSdk 24。这意味着安卓最低版本不能定太低，且 CI 镜像要跟上。0.x 版本 API 会变，必须把它包在自己的 `ReaderView` 接口后面，所有调用点收敛到 `reader/reader_view.dart` 一个文件。

同时它 2026-10 才 0.7.0，虽然活跃但是年轻。**备选**：`epub_viewer` 系列做降级方案，或自研基于 WebView 的阅读器。不建议 v1 自研，分页引擎是三个月起步的坑。

### 10.7 免费 = 所有支持成本在自己身上

没有官方服务器，意味着每一个 WebDAV 配置失败都必须靠页面自己解释清楚。这不是「加分项」，是留存的决定因素。建议把 §9.3 的错误分类当成**核心功能**排期，而不是收尾时的打磨项。

### 10.8 时钟不可信

`updatedAt` 来自设备本地时钟。两台设备差 10 分钟很常见，差几小时也不罕见。

**缓解**：同步时把本机时间与服务器 `Date` 头比对，偏差 > 5 分钟时给该设备的记录打 `clockSkew: true` 标记，合并时对这类记录改用「服务器接收时间」排序。同时 UI 上提示一次「你的设备时间不准，可能影响同步顺序」。

v1 不做向量时钟，但要把这个陷阱写进文档，免得后来人以为是玄学。

### 10.9 书籍文件放不放 WebDAV

用户想法是「可由用户自行放入」。实际风险：坚果云免费版单文件限 100 MB、有流量限制，一本扫描版 PDF 就超。

**调整**：默认**只同步元数据（四个 json/jsonl）**，书文件同步做成每本书的可选项，并在开启时显示体积与预估流量。用户也可以完全手动把 EPUB 丢进 WebDAV 的 `books/<hash>/` 目录。手机端「从 WebDAV 拉书」与「同步」是两个独立动作，不要混在一个按钮里。
