# 独立审计报告（无上下文审计员）

> 审计对象：`dsh-Reading`（DSH 插件 `dsh-reading`）。审计者无本项目历史上下文，只凭代码与可运行命令判断。
> 标注约定：`[实测]` = 我在本机跑出来的；`[读码]` = 读代码推断的，未实机验证。

## 我实际跑了什么

```bash
cd /path/to/dsh-Reading
node golden/run.mjs            # [实测] PASS 318/318，8 个 fixture，vectors.json sha256 已校验
node test/run.mjs              # [实测] 11 个测试文件全通过 / 0 失败

```

三项都直接通过（`jsdom`/`ajv` 已在仓库依赖里，未额外安装）。除此之外我没有找到可用的真实浏览器环境，所以**所有几何、渲染、翻页相关的结论都是读码得出的**，这一条限制了下面第 1 条缺陷的定级。

## 结论

**核心能用的，但还不能就这么发布。** 项目的骨架（CFI 单一锚点、三层校验、覆盖层不改正文 DOM、零依赖）是认真做过的，测试也不是摆设。最大的风险是两处「静默给出错误位置」的路径——翻页位移疑似被减了两次（`annotate.js:298`），以及 L2 结构校验与实际解析用的是两套子节点索引（`cfi.js:463`）——这两种错误都不会报错，只会让划线悄悄偏位。数据层的最大风险不在丢数据，而在**不可信 EPUB 可以绕过解压上限打爆宿主进程**（`zip.js:142`）。

## 我怀疑但没能证实的地方

1. **第 1 条到底成不成立，取决于浏览器是否对 `Range.getClientRects()` 应用祖先 `transform`。** 按规范与 `reader.js:247` 的自述应该是应用了，但我没有真实浏览器可复现。请作者用一行代码定论：在 iframe 里 `body` 设 `translateX(-500px)` 后打印某个 Range 的 `getClientRects()[0].left`，看是否也随之减 500。
2. **高位划线在「窗口缩放」后是否重算。** `annotate.js:341-347` 用 `ResizeObserver` 观察 `containerEl`，`reader.js:503-510` 也有兜底 `resize` 监听；但 `records` 数组的身份没有保证（`annotate.js:373` 依赖 `records` 引用）。如果上层每次渲染新建数组，会 `setBoxes → 重渲染 → 新数组 → 再重算`，可能死循环。没跑 UI 不敢断言。
3. **切章节时旧 iframe 上的监听器是否全部解绑。** `reader.js:503-507` 的 `resize` 分支看着成对，但 `load`/`onPageChange`/`onBadAnchor` 等回调的注册点我没有全量核对到每一处 cleanup。
4. **图片未加载时的分页。** `reader.js:250-258` 用 `scrollWidth`/`documentElement.scrollWidth`/最后一个 `lastElementChild` 的右边界取最大值，比单一量法稳，但仍依赖图片已有布局尺寸。我没有找到「`img` load 后重新 `paginate`」的触发路径；如果确实没有，含大图的章节首次分页页数会偏少，而且之后不会自愈。
5. **jsdom 下的几何断言全是桩坐标**（`test/dom_immutability_test.mjs:200-247`），所以 L3 文本指纹、翻页位移、缩放重排的**坐标正确性**从未被自动化测试覆盖过。这类缺陷只能靠真机。

## 我认为做对了的地方（最多 5 条）

1. `filter` 的传递是完整的：vendor 只有两个几何入口，外层所有调用（`annotate.js:148,273`、`reader.js:267,308,312,475`）都走 `client/src/cfi.js` 的 wrapper，`resolvePoint`（`cfi.js:341`）与 `fromRange`（`cfi.js:612`）各自把 `makeFilter` 传进去了——没有一个 call site 漏传，这正是最容易出错的地方。
2. 「高亮不改正文 DOM」有真测试，不是口号：`test/dom_immutability_test.mjs:75-116` 的指纹把**文本节点按路径索引 + 长度**也算进去，把一个文本节点拆成两个会立刻不等；还额外比对全部属性值（`:372-382`），并用源码黑名单兜底（`:386-390`）。
3. 解压上限放在解压**前**按声明值判（`lib/zip.js:310-320`），解压后再核一次实际长度（`:163`）——思路是对的，只是 `:142` 的 `maxOutputLength` 在 `size===0` 时漏了默认值。
4. XML 解析器真的不展开 DTD / 外部实体：`decodeEntities` 只认五个内置实体和数字实体（`lib/xml.js:63-106`），`DOCTYPE` 只跳过、不记录实体声明，XXE 不成立。
5. 墓碑比较方向是对的：`lib/store.js:565` 的 `>=` 让「后写入的墓碑」在 `(updatedAt, deviceId)` 相等时仍然生效。这个方向最容易写反，作者没写反。
